# kteam web UI — accessibility audit

Independent a11y pass over `modules/kteam-ts/ui/**` after the redesign shipped
(`f6f587d..cf6db97`). Scope: contrast across 5 theme families x light/dark,
keyboard traversal, semantics/live regions, reduced motion, mobile.

The reverted work is a **verified-green diff**, not a sketch: with it applied the

## Running the tool

From `modules/kteam-ts/ui`:

```
bun run a11y:contrast                        # all 10 themes; exit 1 on any hard failure
bun run a11y:contrast --theme=mission-dark   # one theme x mode
bun run a11y:contrast --theme=mission        # both modes of one family
bun run a11y:contrast --suggest              # computed fix per failing token
bun run a11y:contrast --all                  # include PASS rows
bun run a11y:contrast --all --json           # machine-readable
bun run a11y:contrast --help
```

Exit code is 1 on any hard failure or unresolvable token, so it works as a CI
gate. It follows `@import` from `src/index.css`, so it already tracked the tokens
when they moved to `src/themes.css` mid-audit and will survive the next move.

`--suggest` is the part worth using during the rework: for each failing token it
binary-searches the minimal hue-preserving lightness move that clears _every_
pair that token fails, and prints the resulting hex. Mission's cyan stays cyan.

What it accounts for, because each one hides a real failure otherwise:

- **alpha** — Mission's borders/washes are `rgba()`; composited over the actual
  backdrop before measuring.
- **`--chrome-opacity`** — `.kt-chrome` renders `--faint` _at_ that opacity, so
  the effective ink is a blend. Both forms are measured separately.
- **`--bar-bg`** — translucent sticky bars composited over `--bg`.
- **`--body-wash`** — Mission and Ember paint radial gradients over `--bg`; at
  the hot spot the background is not `--bg`. The peak stop is composited and body
  text re-checked. This is what pushed `mission-light --faint` from 4.39 to 4.08.

### The two accessibility CLAIMS — both verified TRUE

I was told not to trust these. They hold.

| Neo-Brutalism "every text/background pair clears WCAG AA" | **HOLDS** | worst body text 5.42:1 (light) / 6.18:1 (dark) |

Both still fail the **`--ring` focus indicator** (F-2 below), which is a
structural bug in a shared CSS rule rather than a palette problem — it is the
only defect in four of the ten themes. Neo's claim says "the focus ring is a 2px
hard rule", and for buttons it is; for text inputs the rule is bypassed.

### Tiering — what is a hard failure and what is advisory

WCAG 1.4.11 asks 3:1 of "visual information required to identify user interface
components and states" and exempts pure decoration. Applying that sentence
honestly means splitting the border tokens, not waiving the number:

- **Hard (3:1)** — `border` (because `input, textarea` draw their edge with it,
  and a field's edge is the only thing that says "you can type here"),
  `accent-border` (carries selected/checked/pressed on 5 controls),
  `focus-color`, `ring` (currently the _sole_ focus indicator on text fields),
  `user-border` (the only marker on a user turn), and the `ok/warn/err/pend`
  fills in `StatusMark` (there, the dot _is_ the information).
- **Advisory (measured, printed, never fails the build)** — `border-soft`
  hairline separators, `code-border`, the `*-border` badge outlines, `user-rail`.
  Each is an edge drawn around something already identified by its own fill and
  its own text label. 100 of the 231 non-passing rows are these. jessica flagged
  the same set as a known debt and asked whether any becomes an affordance:
  **none of them do** — but `--border` does, which is why it is in the hard tier.

Judgement call, stated plainly so it can be overruled: the advisory tier is a
reading of the spec, not a loophole. If the rework wants card edges at 3:1 too,
change `THRESHOLD`/tier in the script and 100 more rows go red.

Structural recommendation for the reworked tokens — **split the border token**:

| new token              | value (10 themes)                                                                                                                                                  | consumers                                                                    |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `--border-strong`      | studio `#868692` / `#6d6d78`, mission `#56838c` / `rgba(151,217,224,0.52)`, neo `#0a0a0a` / `#f5f5e8`, ember `#8c7657` / `#847665`, contrast `#000000` / `#ffffff` | `input`, `textarea`, outline buttons — anything whose edge is the affordance |
| `--border` (unchanged) | as shipped                                                                                                                                                         | cards, panels, table rules — decoration                                      |

Without the split, holding `--border` at 3:1 puts a mid-grey outline on every
card and Studio stops looking like Studio. With it, both constraints hold.

And for `--accent-border`: **stop using it for state.** It is a pale tint that
measures 1.2–2.9:1 against its container in six of ten themes. The five
state-bearing sites should use `--accent` itself — same hue, no identity lost,
and it already has to clear 4.5:1 as link text, so 3:1 as a border is free:
`AgentSidebar.tsx:219,361`, `ThemeToggle.tsx:148,181`, `NewSessionPage.tsx:176`.
`--accent-border` stays fine as the decorative panel/badge outline it is
elsewhere.

Also worth knowing: the ink ramp cannot keep its current spread. With a 4.5:1
floor and four surface levels, `--faint` (must clear `--surface-2`) and `--muted`
(must clear the darker `--surface-3`) have minimums within a hair of each other.
The tiers have to separate by **size** and only secondarily by tone. Budget for
that in the redesign rather than discovering it at the end.

`--user-rail` is declared in all 10 themes and **consumed nowhere in `src/`**.
Dead token; delete it or use it.

## 2. Findings ranked by severity

Severity = (how many users hit it) x (how badly it blocks). F = functional
blocker, S = serious, M = moderate, L = low.

### F-1 · Mobile: the shell is a fixed-height box that the keyboard breaks

`App.tsx:82` — `<div className="flex h-screen h-[100dvh] flex-col overflow-hidden">`.
The shell is exactly the viewport with `overflow-hidden`, so **nothing can scroll
except an inner pane**. Two consequences, and they match the two symptoms the
user reported ("cannot scroll up", "viewport height wrong with the keyboard
open"):

1. **Software keyboard.** `dvh` tracks the _dynamic_ viewport, which on iOS
   Safari does **not** shrink for the software keyboard — the visual viewport
   shrinks while `100dvh` stays the large viewport. The composer and the bottom
   of the transcript go under the keyboard with no way to scroll to them, because
   the shell has `overflow-hidden` and nowhere to give.
2. **No escape hatch.** If any inner scroller mis-sizes at a narrow width, there
   is no page-level scroll to fall back on. On desktop this design is deliberate
   and good (`App.tsx:70-76` explains the 100vh+31px bug it fixed); on mobile it
   removes the only recovery path.

Fix, both halves needed:

- `index.html`: `<meta name="viewport" content="width=device-width, initial-scale=1.0, interactive-widget=resizes-content">` — Chrome/Android then resizes the layout viewport for the keyboard and `dvh` becomes correct.
- iOS has no equivalent, so drive height from the visual viewport: a listener on `window.visualViewport` `resize`/`scroll` writing `--kt-vh: ${visualViewport.height}px` on `:root`, and the shell using `height: var(--kt-vh, 100dvh)`. Keep `100dvh` as the fallback so nothing regresses where the API is missing.

I could not confirm on a real device from here — this is the structural cause
with the specific lines, and it explains both symptoms. Verify on device.

### F-2 · The focus indicator on every text field is below 3:1, in all 10 themes

`index.css`:

```css
input:focus,
textarea:focus {
  outline: none; /* <- kills the real indicator */
  border-color: var(--accent);
  box-shadow: 0 0 0 3px var(--ring); /* <- becomes the ONLY indicator */
}
```

`--ring` is a 0.30–0.42 alpha accent. Composited over the surface it measures
**1.5:1 to 2.9:1** in all ten themes (worst `mission-light` 1.53:1, best
`contrast-dark` 2.80:1) against a 3:1 requirement. This is the only contrast
defect in Neo and High Contrast, and it silently voids their AA/AAA claims for
keyboard users. It also affects the search box, the composer, and every field on
the new-session page — i.e. every text entry path in the app.

Fix: delete `outline: none` and let the existing `:focus-visible` rule (which is
correct — 2px, 3px in High Contrast, per-theme `--focus-color`) do the work.
Keep the border tint and the bloom as _additional_ affordance. Text inputs match
`:focus-visible` on click as well as on Tab, so nothing is lost. Verified: with
`outline: none` removed, `--focus-color` clears 3:1 against every surface in
every theme already.

Also fold the `Composer` wrapper into the same story: it uses
`focus-within:ring-2 focus-within:ring-[var(--ring)]` (`Composer.tsx:110`), same
sub-3:1 problem, on the app's primary control.

### F-3 · Mobile: iOS auto-zooms when you focus the composer

`Composer.tsx:126` — the textarea is `text-[13.5px]`. iOS Safari zooms the page
whenever a focused field's font-size is under **16px**, and because the shell is
a fixed `100dvh` box (F-1) the zoom leaves the user stranded at the wrong scale
with no page scroll. Compounds directly into the "too small / cannot scroll"
report.

Fix: `font-size: 16px` on the textarea below the `md` breakpoint (or globally —
16px in the composer is defensible on its own merits). Do **not** reach for
`maximum-scale=1`/`user-scalable=no`; that would trade this bug for a 1.4.4
Resize-Text violation.

### S-1 · Touch targets below the 24x24 minimum (WCAG 2.2 SC 2.5.8, AA)

Measured from the classes, at the default 13.5px root:

| control                                     | site                                                 | computed        | verdict                                                             |
| ------------------------------------------- | ---------------------------------------------------- | --------------- | ------------------------------------------------------------------- |
| mobile sidebar trigger                      | `AgentSidebar.tsx:638` `px-1.5 py-0.5 text-[11.5px]` | ~22 x 30 px     | **fails** — and it is _the_ control that opens navigation on mobile |
| icon buttons (close, collapse, row actions) | `p-1` + `size={13..14}` icon, ~20 sites              | 21–22 px square | **fails**                                                           |
| badge-style buttons                         | `py-0.5` + 11px text                                 | ~20 px tall     | **fails**                                                           |
| sidebar toggles                             | `h-6` (`AgentSidebar.tsx:217`)                       | 24 px           | passes, exactly at the floor                                        |
| `ViewTabs` tabs                             | `h-6 px-2.5`                                         | 24 px           | passes, exactly at the floor                                        |

Fix: a minimum hit area on interactive elements rather than 20 individual
tweaks — `min-height: 44px; min-width: 44px` under a coarse-pointer query
(`@media (pointer: coarse)`), applied to `button, a[href], [role="button"]`, with
the _visual_ size kept by padding rather than by growing the glyph. 44 not 24
because these are one-handed thumb targets, and SC 2.5.5 (AAA) is the right bar
for a phone-first surface.

### S-2 · The mobile drawer claims to be modal and is not

`AgentSidebar.tsx:551` — `role="dialog" aria-modal="true"`, but:

- **No focus trap.** Tab walks straight out into the page behind. `aria-modal`
  tells assistive tech the rest of the page is unreachable, so AT and reality
  disagree — a screen-reader user tabs into content their AT says is not there.
- **No focus restoration.** On close, focus is lost to `<body>`; the trigger
  (`SidebarDrawerTrigger`, which stays mounted) is never refocused.
- The scrim is a full-screen `<button aria-label="Close the fleet sidebar">`
  (`:552`) and the header X has the _same_ name (`:570`) — the same action twice
  in the tab order, under one name.

jessica flagged the missing trap as a deliberate cut and named the bar herself:
"Escape, labelled close controls, and initial focus are required". Escape (`:531`)
and initial focus (`autoFocusSearch`, `:583`) are done. The gap is the trap and
the restore.

Fix: `SessionDetails.tsx:60-122` **already contains a correct implementation** of
exactly this — Escape, `restoreTo.current = document.activeElement`, panel focus
on open, restore on close guarded by `document.contains`, and a Tab wrap handler.
Extract it as a `useModalFocus(ref, open, onClose)` hook and use it in both
places. Same for `WardenVerdicts.tsx:123` (Escape only, no trap, no restore) and
`ThemeToggle` (which has `returnFocus` but no trap).

### S-3 · Reduced motion is honoured in the CSS and skipped in the components

`index.css` handles its own animations properly — `--overlay-opacity` and
`--glow-alpha` zeroed (so Mission's scanlines and cyan glow do stop), `.shimmer`
stilled with a colour fallback, `.kt-pulse` stopped. The `:root[data-theme]`
specificity note there is correct and worth keeping.

But Tailwind's `animate-*` utilities are separate keyframes and are **not**
covered. Unguarded:

| site                         | animation                                  |
| ---------------------------- | ------------------------------------------ |
| `Harness.tsx:31-33`          | three `animate-bounce` dots                |
| `ToolGroup.tsx:120,149`      | `animate-spin` on the running-tool spinner |
| `SessionChatPage.tsx:647`    | `animate-spin`                             |
| `NewSessionPage.tsx:112,158` | `animate-pulse` skeletons                  |
| `SessionsListPage.tsx:512`   | `animate-pulse` skeleton                   |
| `SessionChatPage.tsx:686`    | `animate-pulse` skeleton                   |

`Composer.tsx:156` _does_ carry `motion-reduce:animate-none` — the pattern is
known, it was applied once and then missed six times, which is exactly the class
of bug a per-component opt-in produces.

Fix: stop opting in per component. One rule in `index.css`:

```css
@media (prefers-reduced-motion: reduce) {
  .animate-spin,
  .animate-pulse,
  .animate-bounce,
  .animate-ping {
    animation: none !important;
  }
}
```

Safe here because every one of these sits next to text that carries the same
fact ("sending…", "running", the skeletons are placeholders). Check that
`ToolGroup`'s spinner keeps a visible non-motion state when stilled — a
motionless spinner glyph is acceptable, an invisible one is not.

### S-4 · Streaming transcript content is never announced

Only one live region exists in the whole app (`Composer.tsx:151`). A screen
reader user gets **no notification** that a teammate started responding, that a
turn finished, that a tool failed, or that the connection dropped and recovered.
The transcript just silently grows.

Making the transcript itself `aria-live` would be the wrong fix and genuinely
worse — a streaming token feed on `polite` is unusable. The right shape:

- one `aria-live="polite" aria-atomic="true"` visually-hidden status region per
  session pane, holding a _summary_ that changes rarely: "Hayden is responding",
  "turn complete, 3 tools ran", "disconnected, reconnecting";
- `role="alert"` (assertive) only for errors that need interrupting — send
  failure, kill, needs-human;
- debounce it. One announcement per state transition, not per token.

There is no `sr-only`/visually-hidden utility in the codebase yet; add one (or
Tailwind's `sr-only`) rather than hiding with `display:none`, which removes it
from the a11y tree entirely.

Note also: `Composer.tsx:151`'s live region wraps the _whole_ hint line, so the
static text ("Enter sends · Shift+Enter newline") is re-announced on every
busy/sending transition. Scope the region to the status words only.

### M-1 · Dashboard table: real headers, missing scope and names

Good news first: it is a genuine `<table>` with `<thead>`/`<th>` (`SessionsListPage.tsx:241-251`),
not a div grid. Gaps:

- `<th>` has no `scope="col"` (`Th`, `:330-340`). Add it — one word, and it is
  what makes header association reliable in older AT.
- One table is rendered **per project group** with no `<caption>` and no
  `aria-label`, so a screen reader hears several unnamed tables. Give each the
  project name (`<caption class="sr-only">` or `aria-label`).
- 6 columns at `text-[10px] uppercase tracking-[0.1em]` headers — legible on a
  desktop, and the cards path covers narrow widths, so not a failure, but 10px is
  the smallest type in the app and it is the row that explains all the others.

### M-2 · `ViewTabs` announces a tab pattern it does not implement

`ViewTabs.tsx:24-48` sets `role="tablist"` and `role="tab"` + `aria-selected`,
but there is no `aria-controls`, the panels have no `role="tabpanel"`/`id`, and
there is no arrow-key handling — every tab is its own tab stop. AT announces "tab
1 of 3" and then arrow keys do nothing.

Fix, pick one and be consistent: either implement the pattern (roving `tabIndex`,
Left/Right/Home/End, `aria-controls` + `role="tabpanel"` with `aria-labelledby`),
or drop the roles and let them be plain buttons with `aria-pressed`. The second
is honest and cheap; the first is better. `ThemeToggle`'s family radiogroup
(`:161-183`) already does the roving-tabindex + arrow-key version correctly and
is the model to copy.

### M-3 · Selected state is conveyed by colour plus a sub-3:1 border

Covered numerically above (`accent-border`), but the semantic half is fine and
worth recording: all five state-bearing controls carry `aria-pressed` or
`aria-checked`/`role="radio"`, so AT gets the state. It is _sighted_ users who
are relying on a 1.2–2.9:1 outline plus a soft tint. Switching to `--accent`
fixes it without touching the markup.

### L-1 · Dead code with its own a11y debt

`FolderSidebar.tsx` (254 lines) is orphaned — jessica confirms it is unused after
the fleet sidebar replaced it. It contains a `role="dialog"` _without_
`aria-modal`, without a trap and without Escape. Not a live defect since nothing
renders it; delete the file so nobody copies the pattern out of it.

### L-2 · Disabled controls at 0.55 opacity

`index.css` `button:disabled { opacity: 0.55 }`. Disabled controls are exempt
from contrast requirements, so this is not a violation — flagging it only because
0.55 on top of an already-quiet token can make a disabled Send indistinguishable
from an enabled one at a glance. Consider distinguishing disabled by something
other than opacity alone.

## 3. What is already right

Worth recording so the rework does not undo it:

- **`StatusMark.tsx`** is a model of not-colour-alone: `role="img"` +
  `aria-label` + `title`, a per-status _shape_ (circle / diamond / square) as a
  second channel, and `aria-hidden` on the inner glyph so it is announced once.
  The `kt-pulse` comment even explains that removing the animation removes
  nothing but motion. Both true and verified.
- **`SessionDetails.tsx`** is a correctly implemented modal — Escape, initial
  focus, Tab wrap, focus restore guarded against a detached node. Promote it to
  a shared hook; do not rewrite it.
- **Icon-only buttons have accessible names.** I checked every one: `aria-label`
  present throughout (`AgentSidebar`, `AppBar`, `SessionHeader`, `ThemeToggle`,
  `SessionDetails`, `TerminalView`). This is the item that usually fails an audit
  wholesale and it is clean.
- **Zoom is not blocked** — the viewport meta has no `maximum-scale` or
  `user-scalable=no`, so SC 1.4.4 passes. Keep it that way while fixing F-3.
- **Theme families differ in more than colour** — type, geometry, border weight,
  shadow model — so High Contrast is a genuinely different design, not a recolor.
  That is what lets it hit AAA.
- The `:root[data-theme]` specificity comment on the reduced-motion block is
  subtle and correct; a bare `:root` there would silently lose to the theme
  blocks and leave the scanlines running.
