# Kteam UI performance pass

## Method

- Built the production UI with `bun run build` before and after the changes.
- Compressed emitted assets with gzip level 9 and Brotli quality 11.
- Measured one fresh Chromium 150 headless browser navigation to the live,
  daemon-served dashboard. Each browser used a new profile and cleared its HTTP
  cache; the daemon was not restarted. `cold load` is navigation duration and
  `FCP` is the browser paint timing. These localhost, single-sample timings are
  useful smoke measurements, not a substitute for throttled field RUM.
- Analysed the bundle with `vite-bundle-visualizer` plus sourcemaps.

The prototype is deliberately **reverted and not deployed**: the lead halted
implementation while the UI enters wider mobile/layout/theme rework. These
numbers preserve a measured decision record for that rework rather than claim a
shipped improvement. The headline prototype improvement is the downloaded and
parsed dashboard JavaScript.
The localhost paint sample did **not** show a measurable latency win, so no
paint-time gain is claimed. A chat route still downloads markdown and
highlighting when it needs them, and chunk boundaries reduce compression
efficiency slightly; it nevertheless downloads about 52 KB less gzip than the
old all-in-one entry.

## Measured prototype (reverted)

1. Chat-route code splitting
   - `SessionChatPage` is a lazy route with a small loading fallback. Markdown,
     transcript, tool-preview, and terminal code now stay off the fleet
     dashboard's first paint.
   - Warden report markdown is also lazy: it downloads only after a reader
     opens a report, rather than because the dashboard merely contains the
     collapsible verdict section.
   - Measured result: dashboard entry fell from 837.0 KB raw / 253.8 KB gzip to
     298.2 KB / 88.7 KB.

2. Restricted syntax highlighting
   - Replaced `rehype-highlight`'s all-language registry and
     `highlight.js/lib/common` with one explicit shared registry. It contains
     the 29 language definitions returned by `langFromPath` plus their required
     dependencies, and handles Markdown fences through a custom code renderer.
   - Bundle analysis: Highlight.js went from about 303.6 KiB across 233 source
     modules to about 137.6 KiB across 31 modules. It now lives in the lazy
     Markdown chunk.
   - Behaviour retained: recognized fenced code and tool-result files remain
     highlighted; unknown languages remain escaped plain text; auto-detection
     remains disabled.

3. One shared usage-feed poll
   - Moved `useUsage` onto the existing `FleetStore`. The store has one
     visibility-gated, 60-second request and publishes a stable indexed
     snapshot to all consumers.
   - Before, the dashboard plus two preserved chat panes could run three
     identical polls. It now runs one; consumers retain the same hook API and
     only the usage slice updates when a response arrives.
   - This is an exact request-count reduction verified from the subscription
     topology; it is not represented as a synthetic browser timing win.

## Findings

- `bun run check` and the production build passed for the prototype. Its code
  and rebuilt `ui-dist` were then reverted at the lead's instruction; this
  report is the sole deliverable from the pass.
- The store already had proper selector granularity: `useSyncExternalStore`
  returns stable fleet/control/search/session slices, per-session buffers are
  bounded (300 events across an LRU of 12 sessions), and targeted refreshes are
  debounced. I left that design intact rather than adding indiscriminate memo
  wrappers.
- Reconnect handling already uses capped exponential backoff with jitter, an
  in-flight reconcile guard, a five-second reconcile minimum gap, and a
  visibility gate. No stampede defect was found.
- Lucide imports were already per-icon and tree-shaken (about 22 KiB), so no
  import rewrite was warranted. `date-fns` was likewise modest (about 22 KiB).
- There is no render-blocking Google Fonts `@import`; the pre-paint theme
  bootstrap is inline, has no network dependency, and preserves the documented
  theme-storage contract. I left it unchanged.
- The reduced-motion rules were already present. No layout-changing animation
  regression was introduced.

## Deliberately not changed

- Transcript virtualization: no representative large-transcript profile showed
  a defect, and changing it risks the documented pointer-latched detach and
  prepend-scroll correction invariants.
- Theme-token CSS: the five-family stylesheet is static selector data, not
  runtime-generated styles. I found no scoped, measured change that justified
  risking the shipped themes. A real style-recalculation profile while switching
  themes would be the right prerequisite for further work.
- The authored redesign-debt document was absent at the start of this pass and
  appeared while work was underway; its listed usage-poll debt informed the
  measured (but reverted) shared-store prototype.
